# Правила работы Claude над проектом

Обязательны для каждой сессии. При конфликте с удобством — побеждают эти правила.

## Приоритеты

1. Целостность данных пользователя.
2. Электрическая корректность и прозрачность ограничений.
3. Переносимость (офлайн, флешка, второй ПК).
4. Эргономика.
5. Внешний вид.

## Порядок работы

- Работать строго по этапам `docs/PLAN.md`. Не начинать следующий этап без подтверждения пользователя.
- Перед изменением перечислить затронутые модули и возможные регрессии.
- Небольшие коммиты, по одному смысловому изменению. Сообщение коммита — по-русски, что и зачем.
- Не переписывать работающие разделы без документированной причины. Не удалять функции и данные, не менять дизайн самовольно.
- Архитектура меняется только через новый ADR и с согласия пользователя.
- Каждый этап завершается отчётом `docs/reports/stage-N.md`: реализовано, проверено (какими тестами), ограничения, что дальше.

## Честность

- Никаких заглушек с фиктивными показаниями под видом готовой функции. Неготовое помечается «не реализовано» / «не поддерживается».
- Симуляция не гарантирует безопасность и работоспособность реальной платы — так и писать в интерфейсе.
- Отсутствие модели, неполные параметры, ошибки сходимости, превышения пределов показывать явно.
- Данные из интернета — только как предложение, с источником; пользователь подтверждает.
- Если внешняя библиотека не подходит или модели нет — сообщить и предложить проверяемую альтернативу.

## Данные

- Любая запись на диск — атомарная (`writeFileAtomic`). Удаление проекта — перенос в корзину.
- Импорт никогда не «чинит» данные молча: ошибки целостности — отказ со списком проблем.
- Связи — только по UUID и номерам выводов, не по координатам и подписям.
- Любое изменение формата — `schemaVersion`/`formatVersion` + миграция + фикстура старой версии + тест.
- Изменения модели детали по умолчанию локальны для проекта; перенос в общий каталог — только с подтверждения.

## Тесты

- Каждая функция этапа — unit/integration/e2e тест. Тесты экспорта/импорта обязательны.
- `npm test` должен проходить перед каждым коммитом в `main`.
- Эталонные задачи (этапы 4–5) — с известными аналитическими ответами и допуском.

## Экономия токенов

- Не перечитывать файлы без нужды; читать нужные фрагменты.
- Не генерировать декоративные экраны и длинные пересказы в ответах.
- Отчёт пользователю — кратко: результат, проверки, ограничения, следующий шаг.
